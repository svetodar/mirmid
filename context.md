# context.md — важная информация о настройках mirmid + замечания по согласованности project.md

## 1. Ключевые факты из project.md (настройки)

- **Язык/платформы:** Python 3.14; Linux / Windows / macOS.
- **Режимы:** утилита командной строки (этап 1, текущий), интерактивный CLI (этап 2).
- **LLM:** любой OpenAI-совместимый API через SDK `openai`; стриминг всегда; reasoning — приглушённым текстом.
- **Логирования нет**; история — только файлы сессий `.mirmid/sessions/<uuid>.md`; ошибки → stderr.

### Системные настройки (`$MIRMID_HOME`)
- Каталог: `MIRMID_HOME`, по умолчанию `~/.config/mirmid` (Linux), `%APPDATA%/mirmid` (Windows), `~/Library/Application Support/mirmid` (macOS).
- `llm.json`: `hosts[] {name, base_url, api_key}`, `models[] {host, model}`, `http {timeout: 900, connect: 10}`.
- API-ключи LLM хранятся **только** здесь (права 0600, кроме Windows); в сессиях и настройках проекта не дублируются. Пароль PostgreSQL — исключение по §4.2: он живёт в `.mirmid/settings.json` (см. замечание 19).

### Настройки проекта `.mirmid/settings.json`
- `version: 1`; `model {name, host, temperature, reasoning}`;
- `tools {shell, postgres, postgres_any_sql, summary_session, db{dbname,user,password,host,port}, check_recursion, max_depth}` — субагенты идут в общем списке с инструментами (по имени);
- `http {timeout, connect}`.
- Приоритет: CLI > настройки проекта > системные > значения по умолчанию (сами дефолты в документе не определены — см. замечание 12).

### Прочие ключевые правила
- Песочница файлов = папка проекта (`_check_path` + `is_relative_to`, как в sqlag.py); запись в `AGENTS.md` и `.mirmid/*` запрещена, чтение разрешено.
- PostgreSQL: psycopg3, одно ленивое подключение на запуск, общее для родителя и субагентов; `execute_sql_query` — только SELECT/INSERT/UPDATE/DELETE/WITH/CALL (валидация pglast), коммит после успеха; `postgres_any_sql` выключен по умолчанию.
- Сессии: markdown + frontmatter (`uuid, parent, restored_from, model "имя @ хост", started, status: finished|interrupted|error`); пишет harness атомарно (tmp + rename) после каждого шага; json в файле не обрезается.
- Восстановление: `--session <uuid> --prompt "..."` → новая сессия, `summary_session` читает старый файл и готовит сводку (`restored_from`); если `summary_session` выключен — ошибка.
- Субагенты: md + YAML frontmatter (name/description/parameters/tools); теги `<param>` подставляются; обязательный параметр не передан → ошибка в контекст родителя; необязательный = пустая строка; набор инструментов = базовые файловые + из frontmatter.
- Рекурсия: стек вызовов (push имя+параметры до вызова, pop после); повторение записи на стеке → ошибка с форматом `{"status":"error","message":...,"calls":[...]}`.
- Вывод rich: reasoning-блоки по `\n\n` печатаются статично над Live; панели инструментов; усечение JSON на экране до 16 строк (8+…+7), в контекст модели — полный результат.
- i18n: gettext, базовый язык en, поставка с ru; локаль из `LANG`/`LC_ALL`; язык ответа модели привязан к локали через системный промпт.

### 2.1 Противоречия (нужно исправить документ)

1. **[осталось] `max_depth` — двойное определение (§7).** «ограничение глубины вложенности (`tools.max_depth` по умолчанию 10, если отсутствует, то нет ограничений глубины)». Если дефолт = 10, то при отсутствии должно быть 10, а не «без ограничений» (в примере §4.2 стоит `max_depth: 10`). → Выбрать одно поведение и описать в одном месте.
2. **[осталось] Набор инструментов субагента: §3 против §7.** §3: «набор инструментов = базовые файловые + перечисленные в frontmatter». §7 добавляет: «Если среди доступных есть другие субагенты — их можно вызывать». Неясно, получает ли субагент автоматически **все** включённые в проекте субагенты или только явно перечисленные в его `tools:`. → Уточнить и привести оба раздела к одному тексту.
3. **[осталось + уточнено] Пакетный режим: маппинг строк списка на параметры субагента.** §2.3: строки `routines.txt` «передается в обязательном параметре routinename»; §12: «запуск любого субагента для каждой строки с параметрами: `объект` [, `доп. информация`]». Как значения из строки `X[:Y]` сопоставляются с именованными параметрами frontmatter (по порядку? первый обязательный + первый необязательный?) — не определено; для субагента с N параметрами правила нет. **[новое]** дополнительно: в прототипе строка режется по **всем** `:` (`s.split(':')`, берутся только первые две части — всё после второго `:` теряется), а список обрабатывается как `sorted(set(...))` (дедупликация + сортировка). В mirmid нужно явно записать: разбивка по первому `:`, сохраняется ли порядок строк, нужна ли дедупликация.

Не описано и поведение, если модель/хост из настроек не найдены в реестре.
5. **[осталось] Включение кастомных субагентов.** §2.2: «включаются настройкой проекта», но в примере §4.2 показан только `summary_session`. Явно не сказано, что кастомные включаются/выключаются своим именем в том же списке (предполагается из §4.2 «Субагенты в общем списке с инструментами»).
6. **[осталось] Семантика `model.reasoning`** (§4.2) нигде не объяснена. Нужно определить: как флаг маппится на API, применяется ли ко всем запросам сессии, что выводится при выключенном reasoning.
7. **[осталось] Порядок создания сессий при восстановлении.** §6: «каждый запуск субагента — отдельная сессия со ссылкой parent». 8. **[осталось] Поведение при превышении `max_depth`** не определено (в отличие от рекурсии, для которой задан формат ошибки). **[новое]** также неясно, что именно считается глубиной: «ограничение глубины вложенности … для инструментов и субагентов» — вложенность возникает только через субагент→субагент; вероятно, имеется в виду размер стека вызовов (см. §4.2) — сформулировать явно.
