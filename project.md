# Описание проекта mirmid

Документ описывает архитектуру и план разработки ИИ-агента **mirmid**, с учетом уже реализованных в прототипе `sqlag.py` решений.

---

## 1. Суть проекта

mirmid — локальный harness для ИИ-агента:

- **Язык:** Python 3.14, кроссплатформенно (Linux / Windows / macOS).
- **Два режима работы:**
  1. **CLI** — интерактивный многоходовой диалог с продолжением сессии по UUID (этап 2).
  2. **Утилита командной строки** — запуск с параметрами, однократное выполнение задачи (этап 1).
- **LLM:** любой OpenAI-совместимый API (DeepSeek, LM Studio, Ollama и т. п.) через SDK `openai` — как в `sqlag.py`.
- **Вывод:** стриминг всегда; markdown от модели рендерится через `rich`; рассуждения модели (reasoning) показываются приглушенным текстом.
- **Логирования нет** — единственным хранилищем истории являются файлы сессий в `.mirmid/sessions/`. Ошибки выводятся в stderr.

#### Принципы обработки ошибок

| Ситуация | Поведение |
|---|---|
| Ошибка выполнения инструмента (файл не найден, SQL-ошибка и т. п.) | Результат `{"status": "error", ...}` возвращается в контекст модели, агент продолжает работу |
| Ошибка API/сети, обрыв стрима, неверный ответ модели | Работа прерывается; сессия сохраняется со статусом `interrupted`/`error`, выводится понятное сообщение |
| Пропущен обязательный параметр субагента | В контекст возвращается ошибка с текстом о недостающем параметре (модель может поправить вызов) |

## 2. Этапы разработки

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **0. Каркас** | Структура пакета, загрузка настроек (системные + проекта), i18n-скелет (ru/en), определение проекта по `AGENTS.md` | `mirmid --help` работает в пустой и в проектной папке |
| **1. Утилита командной строки** *(текущий)* | Ядро агента, инструменты, субагенты, сессии, стриминговый UI | Все команды из раздела 2.3 работают локально |
| **2. Интерактивный CLI** | Многоходовой диалог, команды `/new`, `/model`, `/host_list`, `/model_list`, `/model_add`, `/model_remove`, продолжение сессии по UUID в диалоге | Диалог с переключением модели и восстановлением сессии без перезапуска |
| **3. Упаковка** | `pip`/`uv tool install`, обвязка для Windows (аналог `taskag.cmd`), документация, примеры субагентов в поставке | Установка одной командой на всех трех ОС |

### 2.1 Тестирование

Для тестирования использовать модель из LM Studio.

### 2.2. Состав этапа 1 (утилита)

- Определение проекта: текущая папка = проект; маркер — файл `AGENTS.md`. Если его нет — понятная ошибка с инструкцией создать его (интерактивное «предложить создать» появится в CLI-режиме, т. к. утилите не с кем договариваться). Папка `.mirmid/` создается автоматически при первом запуске.
- Запуск задачи: промпт из аргумента `--prompt/-p` или файла `--file/-f`.
- Агентский цикл: модель → вызовы инструментов → результаты в контекст → … до финального ответа.
- Инструменты: файлы (песочница = папка проекта), PostgreSQL (опционально, включается настройкой).
- Субагенты из `.mirmid/subagents/*.md` + встроенный `summary_session` (включен по умолчанию, на английском), включаются настройкой проекта.
- Сессии: запись в `.mirmid/sessions/<uuid>.md`; восстановление через `--session <uuid> --prompt "..."` с подготовкой сводки субагентом.
- Пакетный режим (обобщение `-l` из sqlag.py): запуск одного субагента на каждый объект из списка.
- Стриминговый вывод rich, i18n (ru по умолчанию при русской локали системы).

### 2.3. Интерфейс командной строки (этап 1)

```text
mirmid --prompt "Опиши структуру проекта"
mirmid -f task.md                          # промпт из файла
mirmid --session <uuid> --prompt "Продолжи рефакторинг инструментов"
mirmid --subagent create_routine_description --list routines.txt # create_routine_description - субагент в тестовом проекте, routines.txt - список объектов по одному на строку -> передается в обязательном параметре routinename
mirmid --model deepseek-flash --temperature 0.3 --prompt "..."
```

Параметры командной строки имеют приоритет над настройками проекта, те — над системными, те — над значениями по умолчанию.

## 3. Архитектура и структура пакета

```text
mirmid/
├── __main__.py          # точка входа: python -m mirmid / консольный скрипт mirmid
├── cli.py               # argparse, режим утилиты (этап 1)
├── console_ui.py        # интерактивный CLI + команды /... (этап 2)
├── core/
│   ├── agent.py         # основной цикл: запрос к модели → dispatch инструментов → повтор
│   ├── llm.py           # клиент OpenAI-совместимого API, таймауты httpx
│   ├── streaming.py     # обработка стрима: reasoning-блоки, аккумулятор tool_calls
│   ├── session.py       # создание/запись сессий md, восстановление через summary_session
│   └── context.py       # сборка системного промпта и списка сообщений
├── config/
│   ├── settings.py      # загрузка и валидация: системные + настройки проекта
│   └── llm_registry.py  # хосты и модели (основа для /host_list, /model_* на этапе 2)
├── tools/
│   ├── base.py          # протокол Tool: name/description/parameters/run(), реестр
│   ├── files.py         # file_list, exist_file, read_lines, read_text_file, write_text_file, copy_file
│   ├── shell.py         # bash/cmd — опционально (этап 2)
│   └── postgres.py      # execute_sql_query, execute_any_sql, get_table_def_from_db, get_routine_def_from_db
├── subagents/
│   ├── loader.py        # парсинг .mirmid/subagents/*.md и встроенных определений
│   ├── runner.py        # валидация параметров, подстановка тегов <param>, запуск вложенного агента
│   └── builtin/         # summary_session.md (EN)
├── ui/
│   └── render.py        # rich: Live-вывод стрима, панели инструментов, усечение длинных результатов
└── i18n/
    ├── __init__.py      # gettext, определение локали
    └── locales/         # ru (l10n), en (базовый)
```

Каждый инструмент описывает себя (имя, описание, JSON-схема параметров) и реализует `run()`.
Список инструментов для модели собирается из реестра с учетом настроек проекта.
Это же реестр используется субагентами: их набор инструментов = базовые файловые + перечисленные в frontmatter.
Frontmatter везде в формате YAML.

При разработке проекта в каждой папке со скриптами необходимо поддерживать файл description.md с описанием семантики и логики работы скриптов в данной папке, а также test.py с юнит тестами. 
Комментарии в скриптах - только то, что было сделано конкретно сейчас, на русском языке, со временем комментарии должны удаляться.
При разработке проекта поддерживать файл README.md с общим описанием проекта.

## 4. Настройки

### 4.1. Системные (на все проекты)

Хранятся в JSON-файлах в каталоге, задаваемом переменной окружения `MIRMID_HOME`, по умолчанию — стандартное для ОС место конфигурации: `~/.config/mirmid`, `%APPDATA%/mirmid`, `~/Library/Application Support/mirmid`.

```json
// $MIRMID_HOME/llm.json  — основа для /host_list и /model_* (этап 2)
{
  "hosts": [
    {"name": "deepseek", "base_url": "https://api.deepseek.com", "api_key": "sk-..."},
    {"name": "lmstudio", "base_url": "http://192.168.3.98:1234/v1", "api_key": "OPENAI_API_KEY"}
  ],
  "models": [
    {"host": "deepseek", "model": "deepseek-flash"},
    {"host": "lmstudio", "model": "qwen3.8-27b@q6_k_m"}
  ],
  "http": {
    "timeout": 900, 
    "connect": 10
  }
}
```

Ключи доступа хранятся только здесь (права на файл 0600, кроме Windows), в сессии и в настройках проекта не дублируются.

### 4.2. Настройки проекта — `.mirmid/settings.json`

```json
{
  "version": 1,
  "model": {
    "name": "deepseek-flash",
    "host": "deepseek",
    "temperature": 0.1,
    "reasoning": true
  },
  "tools": {
    "shell": false,
    "postgres": true,
    "postgres_any_sql": false,
    "summary_session": true,
    "db": {"dbname": "test", "user": "test_owner", "password": "...", "host": "localhost", "port": 5432},
    "check_recursion": true,
    "max_depth": 10
  },
  "http": {
    "timeout": 900, 
    "connect": 10
  }
}
```

Параметры подключения к PostgreSQL — в настройках проекта.
`postgres_any_sql` (инструмент без ограничений) выключен по умолчанию.
Субагенты в общем списке с инструментами.
Для проверки на рекурсию необходимо поддерживать стек вызовов, куда перед вызовом инструмента пушить его имя и значения переданых параметров. После вызова выполнять pop. Признак рекурсии - повторение этой информации. 

Формат ошибки рекурсии: 

```json
{
  "status":"error", 
  "message": "Обнаружена рекурсия, субагент вызывает себя с одинаковыми параметрами", 
  "calls": [
    {
      "name": "<имя инструмента>", 
      "params": [{"<имя параметра>": "<значение параметра>"}, ...]
    }, 
    ...
  ]
}
```

- Файлы сессий пишет сам harness (атомарно: запись во временный файл + переименование), а не модель.

## 6. Сессии

Формат файла `.mirmid/sessions/<uuid>.md` — markdown с полной информацией о размышлении, использования инструментов и ответах модели, json не обрезается, плюс frontmatter с машинными данными (frontmatter нужен для связей parent/child и статуса; тело остается человекочитаемым):

````markdown
---
uuid: 3f2c1a...
parent: null              # для сессий субагентов — uuid родительской сессии
restored_from: null       # если сессия восстановлена из другой
model: deepseek-flash @ deepseek
started: 2025-01-15T10:00:00+03:00
status: finished          # finished | interrupted | error
---

## user
Текст промпта...

## agent · thinking
Рассуждения модели (если были)...

## tool · execute_sql_query

```sql
SELECT ...
```

#### result
```json
{ "status": "success", ... }
```

#### agent
Финальный ответ в markdown.
````

Правила:

- Файл дописывается/перезаписывается атомарно после каждого завершенного шага (ответ модели или результат инструмента) — при сбое не теряется история и не получается битый файл.
- **Восстановление частичное**: `mirmid --session <uuid> --prompt "..."` → создается новая сессия, субагенту `summary_session` передаются uuid старой сессии и уточняющий промпт; он читает `.mirmid/sessions/<uuid>.md` файловыми инструментами и готовит сводку с нужными акцентами. Сводка + промпт пользователя становятся начальным контекстом новой сессии (`restored_from: <старый uuid>`). Если в инструментах `summary_session` выключен, то данный режим должен завершаться с ошибкой.
- Каждый запуск субагента — отдельная сессия со ссылкой `parent` (в пакетном режиме null).

## 7. Субагенты

Определение — файл markdown с frontmatter:

```markdown
---
name: summary_session
description: >
  Формирует сводку по сессии <uuid> с учетом уточняющего текста <prompt>.
parameters:
  - name: uuid
    required: true
    description: UUID сессии, по которой нужна сводка
  - name: prompt
    required: false
    description: Уточняющий текст (акценты) для сводки; по умолчанию пустая строка
tools: []                 # дополнительные инструменты сверх базовых файловых
---

Ты — субагент, готовящий сводку сессии агента.
Сессия хранится в файле `.mirmid/sessions/<uuid>.md`. Прочитай его и подготовь
структурированную сводку: цель, выполненные шаги, ключевые решения, текущее состояние.

<prompt>
```

Механика:

- Перед запуском теги `<param_name>` в промпте заменяются значениями параметров. Обязательный параметр не передан → в контекст родителя возвращается ошибка с текстом о недостающем параметре. Необязательный по умолчанию — пустая строка.
- Начальный контекст субагента = только его промпт (после подстановки). Системный промпт, дата/время и ОС добавляются как в основной сессии.
- Набор инструментов = базовые файловые (папка проекта) + перечисленные в frontmatter. Если среди доступных есть другие субагенты — их можно вызывать.
- Родителю возвращается финальный текст; передача результата файлами или через БД возможна, если это описано промптом субагента.
- Защита от рекурсии: поддержка стека вызовов с проверкой (раздел 4.2), ограничение глубины вложенности (`tools.max_depth` по умолчанию 10, если отсутствует, то нет ограничений глубины) для инструментов и субагентов.
- Встроенные (`summary_session`) поставляются на английском, лежат в пакете (`mirmid/subagents/builtin/`) и включаются в списке инструментов. Кастомные (например `create_routine_description`) — в `.mirmid/subagents/`, язык произвольный.
- Все субагенты используют **одно текущее подключение к PostgreSQL** родителя (раздел 8), если необходимо им для работы.

## 8. Инструменты

### 8.1. Файлы (всегда доступны, песочница = папка проекта)

Переносятся из `sqlag.py` с теми же именами и семантикой:

| Инструмент | Описание |
|---|---|
| `file_list(folder, mask)` | Список файлов: имя, размер, blake2b-хеш (4 байта) |
| `exist_file(filename)` | Проверка существования |
| `read_lines(filename, first_line?, last_line?)` | Срез строк по индексам как в Python |
| `read_text_file(filename)` | Содержимое файла |
| `write_text_file(filename, content)` | Создание/перезапись (создает родительские папки) |
| `copy_file(source, destination)` | Копирование с сохранением метаданных |

Песочница — подход `_check_path` из sqlag.py: разрешение пути + проверка `is_relative_to(папка проекта)`, абсолютные пути вне проекта отклоняются. Дополнительно: запись в `AGENTS.md` и `.mirmid/*` запрещена (раздел 5). Все ошибки возвращаются как `{"status": "error", "message": ...}` — агент не прерывается.

### 8.2. PostgreSQL (опционально, включается настройкой проекта)

Реализация на **psycopg3 с t-строками** (`conn.execute("... %(name)s ...", {...})`) вместо psycopg2 из sqlag.py. Подключение одно на запуск, ленивое открытие, общее для родителя и всех субагентов; закрывается при выходе.

| Инструмент | Описание |
|---|---|
| `execute_sql_query(query)` | Только `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `WITH`, `CALL`. Валидация — парсер pglast. Коммит после успешного выполнения. |
| `execute_any_sql(query)` | Любые команды (DDL и т. п.) — отдельный инструмент, выключен по умолчанию (`postgres_any_sql`) |
| `get_table_def_from_db(tablename)` | Описание таблицы: комментарии, столбцы с типами/ограничениями, индексы, триггеры — запросы к pg_catalog из sqlag.py переносятся как есть |
| `get_routine_def_from_db(routinename)` | Определение функции/процедуры (`pg_get_functiondef`) — из sqlag.py |

Результаты возвращаются JSON-ом; date/datetime/uuid сериализуются в строки (как в sqlag.py). Ошибки SQL → `{"status": "error", ...}` в контекст, работа продолжается.

### 8.3. Shell (bash/cmd)

Только опционально (`tools.shell`), по умолчанию выключен; реализуется на этапе 2 вместе с интерактивным CLI.

## 9. Стриминг и вывод (rich)

Переносится механика `process_stream` из sqlag.py, вынесенная в `core/streaming.py`:

- **Reasoning:** блоки размышлений разделяются двойным переводом строки; завершенные блоки печатаются статично над Live-областью приглушенным курсивом, текущий незавершенный блок рендерится внутри `Live`.
- **Контент:** накапливается и рендерится как `rich.markdown.Markdown` в том же Live.
- **Tool calls:** аккумулятор по индексу (`tc.index`) — имя и аргументы собираются из дельт до конца стрима.
- **Панели инструментов** (как в sqlag.py): SQL-запрос — `Syntax` с подсветкой, результаты — JSON; длинный вывод на экран усечается до 16 строк (8 сверху + `...` + 7 снизу), **в контекст модели уходит полный результат**.
- **Таймауты:** `httpx.Timeout(900.0, connect=10.0)` — стриминг держит соединение живым во время долгого «размышления» модели. Значения настраиваемые.

## 10. i18n / l10n

- Механизм — `gettext` (stdlib), каталоги в `mirmid/i18n/locales/`: базовый язык интерфейса — английский, поставка включает русскую локализацию.
- Локаль определяется из системных переменных (`LANG`/`LC_ALL`); при русской локали UI и сообщения об ошибках — на русском.
- **Язык ответов модели** привязан к текущей локализации: в системный промпт добавляется инструкция «Отвечай на русском языке» (или аналог). Встроенные субагенты поставляются на английском — их ответы транслируются родителем, если это важно для задачи.

---

## 11. Системный промпт

Собирается в `core/context.py` из:

1. Содержимого `AGENTS.md`;
2. Блока окружения: текущие дата и время, ОС (platform), путь к папке проекта;
3. Инструкции о языке ответа (по локали).

Описания инструментов и субагентов в промпт не включаются — они передаются через параметр `tools` API (субагент становится инструментом с описанием из frontmatter и строковыми параметрами).

## 12. Что берем из sqlag.py

| Идея из sqlag.py | Где в mirmid | Изменения |
